# DEV — 어떻게 만들 것인가

> 대상: **규제 기사 하나를 던지면, 임원 보고까지 끝나 있게 한다.** (From one link to a boardroom deck.)

이번 MVP의 본질은 새 파이프라인을 만드는 게 아니다.
**이미 CLI로 돌아가는 파이프라인(`dt-regulation-brief` 스킬 + `ppt-designer` + 파이썬 3종 스크립트)을 웹 화면으로 올리는 것**이다.
그래서 개발의 90%는 "AI가 뭘 할지"가 아니라 **"CLI 대화로 하던 승인 3번을 화면의 버튼 3개로 바꾸는 것"** 이다.

---

## 1. 개발 구조 선택

### 고른 것: **단일 파일** (`index.html` + `client.js` + 얇은 `server.js`)

1. **DB가 필요 없다.** 미션이 "보고서 이력 검색·태깅"과 "협업·계정·권한"을 안 하는 것으로 못박았다. 남는 상태는 진행 중인 잡 하나뿐이고, **진실의 원천은 이미 `C:\수경_에이전트파일다운\<제목>_<YYYYMMDD>\` 폴더**다. 테이블을 만들 이유가 없다.
2. **서버는 있어야 하지만 얇다.** 브라우저는 `py -3`를 못 돌리고 API 키를 못 숨긴다. 그래서 `server.js`가 필요하지만, 하는 일은 **파이썬 스크립트 spawn + LLM 호출 + 잡 상태 Map 관리**뿐이다. 로직은 전부 이미 있는 스크립트 안에 있다.
3. **파이썬 의존이 배포처를 결정한다.** 산출물 생성이 `python-docx`/`python-pptx`에 묶여 있고, 결과 파일이 **사용자 PC의 다운로드 폴더에 떨어져야** 한다. 로컬에서 도는 얇은 노드 서버가 가장 정직한 답이다. (아래 "배포 리스크" 참조)

> 화면은 `index.html` 한 장(해시 라우팅 없음, 잡 하나 = 화면 하나). 파일 구성: `index.html` / `client.js` / `server.js` / `.env` — 기존 앱들과 같은 3파일 패턴.

### 버린 것
- **Supabase 기반** — 로그인도 이력 저장도 MVP 범위 밖이다. 유일한 영구 저장소는 이미 로컬 폴더다. DB를 붙이면 "안 하는 것"을 하게 된다.
- **Next.js 풀스택** — SEO도 라우팅도 필요 없고, 빌드 체계가 늘면 `py -3` spawn·한글 경로·파일 스트리밍만 더 복잡해진다. 혼자 쓰는 내부 도구에 프레임워크 세금을 낼 이유가 없다.

### ⚠️ 배포 리스크 — 이 구조 선택의 진짜 이유 (확인 필요)

| 질문 | 현재 판단 |
|---|---|
| Vercel 서버리스에서 `python-docx`/`python-pptx`를 돌릴 수 있나? | **확인 필요.** Vercel에 Python 런타임 자체는 있지만, ① 함수 실행시간 상한(Opus 보고서는 분 단위) ② 파일시스템이 `/tmp` 외 읽기전용 ③ 결과물이 **내 PC 폴더**에 떨어져야 한다는 요구 — 세 가지가 전부 걸린다. |
| 그래서 MVP는? | **로컬 실행 확정.** `node server.js` → `http://localhost:3300`. 기존 앱들이 쓰는 3000번은 피한다(하나씩 실행 원칙). |

**안 될 경우의 대안 (Phase 4에서 결정, 지금 고르지 않는다)**
- **(A) 로컬 실행 유지** — MVP 기본값. 동료 공유는 "이 폴더 받아서 `start.bat` 실행" 수준으로 충분하다.
- **(B) 웹+로컬 워커 분리** — 화면만 Vercel, 문서 생성은 내 PC의 워커가 잡을 폴링해 처리. 협업이 필요해지면 그때.
- **(C) Node 라이브러리 전환** (`docx`, `pptxgenjs`) — 서버리스는 되지만 **검증 끝난 `render_ppt.py`(네이티브 차트·브랜드 컬러)를 버리게 된다.** 비용 대비 최악. 최후의 수단.
